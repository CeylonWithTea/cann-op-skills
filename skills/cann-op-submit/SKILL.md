# CANN 算子提交

完成可复核的提交内容，再根据用户已有发布授权执行推送、创建或更新 issue/PR。使用 skill、生成文案或编写代码本身不自动授予对外发布权限。用户已经明确要求提交到指定仓库/分支时，沿用授权，不再逐步重复询问。

## 按请求选择范围

- **仅撰写/修改正文**：读取需求、最终差异和已有验证证据后完成文案；不要求提交身份或认证、不创建分支、不自动重跑构建，也不追问是否发布。证据不足的结论明确标记，不编造结果。
- **准备可提交的改动**：执行适用的分支、差异、自审和验证检查。仅在需要实际创建 Git 提交时补齐提交身份，发布凭据可以留到发布阶段。
- **发布或评审整改**：在用户指定范围内执行下面的发布步骤；只有任务要求发布但缺少必要目标/授权时，完成本地准备后再集中询问。

下面各节按所选范围执行，不是每次调用都必须走完的流水线。

## 先核对上下文

- 目标平台、上游仓库与目标分支，当前远端、branch、工作区差异、已有 issue/PR。
- 读取目标仓当前 CONTRIBUTING、PR/issue 模板、CI/pre-commit 配置和许可要求，避免固定历史 clang-format 版本或构建参数。
- 在需要提交/发布时复用用户已确认的 fork、账号、提交姓名/邮箱与认证方式。缺失且本次执行必需的项目集中询问；可从本地配置读出候选，但不要把未知身份直接用于提交。
- 认证只记录 SSH key 路径/指纹、agent 或 credential helper 引用。让用户在安全入口配置 token/密钥，不要求在对话、skill 或支持文档中贴私钥/口令。

## fork 与分支

同一个上游仓库且没有访问/协作隔离要求时，复用一个用户主 fork；多个算子各建独立功能分支，不为每个算子新建 fork。环境不同通常由独立构建目录/容器解决，也不必自动增加 fork。

本地优先用 worktree 建立 `ops-cv_<算子>`。分支名沿用已有约定；新任务建议算子名 snake_case，先检查冲突。每个独立算子从目标上游基线创建，不从另一个未合入算子分支派生；确有依赖则明确 PR 顺序和依赖提交。

```bash
# 示例：变量由本任务实际仓库与已确认分支填写，不能原样执行
git -C "$REPO_DIR" fetch upstream
git -C "$REPO_DIR" worktree add -b "$OP_BRANCH" "$OP_WORKTREE" "$BASE_REF"
```

执行前检查远端/路径/分支存在性及用户未提交改动。不重命名现有 fork、不 reset 用户工作区、不默认 force-push。已有共享分支需改历史时说明影响并取得对应授权；普通本地修复与检查继续推进。

## 最终差异与验证

1. 看相对实际目标基线的完整 diff，而非只看最后一次 commit。明确列出本次算子与必要注册/构建/文档文件，不使用无范围的 `git add .`。
2. 去除误入提交的 build、私有包、临时日志、demo 快照、认证信息及其他算子改动。公共脚本默认不在算子修改范围内；确属上游功能需要时取得范围授权，不能用它修补本地旧包混用问题。
3. 运行适用的格式、拼写、许可、构建和测试，使用最新提交形态。核实关键数值回归、golden、benchmark 与运行说明能够交付；生成式 ACLNN 也要有可用的生成/打包链路和接口文档。
4. 做一次 `cann-op-review` 或等效最终自审。报告实际验证数量、版本与限制；不能以总用例数替代关键路径覆盖。
5. 文档变更与代码一致：性能表注明设备、口径、矩阵、基线、慢例；没有实测的内容写待验证。核对 issue 中承诺的收益与最终实现，不把优化目标写成已达成结果。

## issue 与 PR

正文存放在 `support_docs_<算子>/`。新项目使用 `issue.md`、`pr.md`；继承项目保留已有 `ISSUE_DESCRIPTION.md`、`PR_DESCRIPTION.md`。优先使用目标仓当前模板，没有可用模板时采用 [正文模板](assets/issue-pr.md) 的对应部分。

- issue：说明需求、参考来源、用途、支持范围、接口/设计和验收目标。需求阶段写目标，不能预填成功数据。
- PR：说明最终行为、关键改动、关联 issue、构建/测试、性能与限制，以及接口文档位置。让未读过会话的审查人能理解。
- 发布前核对 fork/head/base、标题、正文和关联 issue。优先查找已有同分支 PR，避免重复创建。任务包含发布但授权范围不明确时，先完成本地准备，再一次性给出具体待发布内容与目标供用户决定；仅要求文案时交付文案即可。
- 平台工具/CLI 可用时优先使用；不假设某台机器安装了特定 CLI。多行正文使用结构化参数或文件输入，避免 shell 拼接破坏换行或触发命令替换。

## 发布后与评审

记录 issue/PR 链接、源分支和提交。按任务授权检查最新 SHA 对应的 CI/CLA/SCA 状态；本地通过不能代替平台状态。轮询采用合理间隔，遇到外部审批或平台故障时报告状态，不无限重试同一失败动作。

评审先验证事实，再修复、补测、更新文案并推送已授权分支。回复评论属于对外发言，需用户明确授权或任务明确包含评审回复；只有代码更新授权时可以先准备回复草稿。保留合理反证，不为了“消除评论”做无依据改动。

提交成功不等于合入；合入后更新支持目录当前状态。删除分支/worktree、清理历史证据或修改 fork 设置不随 PR 提交自动执行。
