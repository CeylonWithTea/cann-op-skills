# CANN 算子开发

将算子交付为可构建、可验证、可复现的代码和文档。默认由当前 Agent 连续执行，不要求 PM、子 Agent、workflow YAML、逐节点审批或逐次确认。遵守目标仓库实际约定；存在无法由用户既有指令解决的冲突时，指出具体冲突，不能宣称 skill 自动覆盖项目规则。

## 开始与继承

1. 读取当前源码、Git 分支/差异、算子支持目录和最新相关评审。历史总结是线索；发现差异时按当前源码和对应版本证据修正认识。用户已明确的目标、约定和授权直接沿用。
2. 区分新开发、补功能、修复和优化，只执行本次需要的部分。继承任务不重建已有目录、不重做已经有效的调研与测试。
3. 在实现前，按 [规格与参考](references/spec-and-research.md) 收敛数学语义、接口、精度、环境和交付标准。集中询问真正影响结果且尚未明确的事项，提供建议；不要把全部模板字段变成问卷。
4. 将长期约定记入支持目录 README。开始后在约定范围内自主修改代码、补测、调整 tiling 和更新不合理的实现结构 UT。改变对外语义、验收标准或授权范围才重新询问；未答复不算批准。

## 调研与工程准备

- 寻找其他仓库的同名实现或等价组合，再查 CANN 仓内相近算法、接口、搬运和测试组织。分别说明语义参考、实现参考和性能基线；同名不保证等价。查阅适用版本的官方 API 资料，不凭其他芯片的示例推断支持能力。
- 形成数据格式表和简短的算法、tiling、资源预算说明。数据表沿用现有 11 列格式，表头与精度约定见 [规格与参考](references/spec-and-research.md)。不要求另起一套大型设计文档。
- 按 [目录与记录](references/layout-and-records.md) 建立 `ops-cv_<算子>` 与 `support_docs_<算子>`。其他仓库采用其实际仓名；已有有效路径保持原状。
- 确认已有环境能满足本次任务。环境变动、版本不明或加载异常时使用配套 `cann-op-env-check`；无需新建容器或重新安装 CANN。缺少该 skill 时直接核对工具链、目标设备、依赖和实际加载的包，不能跳过这些事实检查。

## 从正确实现到 demo 迭代

1. **最小正确版本**：先实现约定的核心路径，同时建立独立 golden、Host UT 和真实 kernel/运行时验证。逐步增加 dtype、模式、边界和规模，未完成能力标清，不将部分通过写成全规格完成。
2. **测试可判定**：检查退出码、实际执行数量和失败数量；零测试、跳过、编译成功不能冒充数值通过。测试须调用生产实现，不能只运行模拟公式。具体覆盖与比较要求见 [验证与性能](references/validation-and-performance.md)。
3. **一次明确改进**：根据瓶颈选择一个可归因的功能或性能变化。代码变更后构建并确认加载新包，先跑受影响 UT/数值测试，再自审和测性能。
4. **自审嵌入迭代**：使用配套 `cann-op-review`，按实际改动选择检查项。若未安装，至少复核语义、尾块/halo、缓冲与同步、精度、真实分支覆盖及构建包一致性。发现问题先修复并复验，再作性能裁决。
5. **成功才封存**：封存前完成本版支持范围的回归及对应验收；性能迭代需有同条件比较和退化说明。通过后递增 `demoN`，保留源码标识与复现入口。失败候选仅记录尝试与原因，不占成功 demo 编号。后来发现旧 demo 不合格，标记失效且保留历史。

每版在一份迭代记录中追加改动、验证、性能、退化/限制、源码版本和复现入口。扩展功能但性能持平的版本可以合格；只通过少量 smoke 的优化不能封存。超过预期投入仍无收益时，保留最佳合格版本并说明限制，不为追求数字修改 golden、放宽容差或隐藏慢例。

## 交付与提交

- 最终提交形态重新构建并执行适用回归；删除/迁移测试文件、接口变化或评审修复后检查受影响的验证。仅文案/格式变化按实际影响检查，避免无意义地全量重跑。
- 保留可执行的关键回归与必要 benchmark，使新机器能复核 PR 的主要结论；巨量原始数据不必进入源码仓。支持目录保存调研、迭代和性能结果。
- 更新算子 README、仓库要求的 ACLNN 接口文档，以及支持目录的 issue/PR 正文。优先采用目标仓当前模板；新任务默认 `issue.md` / `pr.md`，继承任务保持已有名称。
- 提交时使用配套 `cann-op-submit`。未安装时遵循目标仓贡献指南，检查 fork/分支、提交范围、身份与已有发布授权；不能因使用开发 skill 自动推送或对外发帖。
- 交付说明列出位置、已验证范围、未完成项和复现入口。合入状态以平台或用户提供的可靠信息为准，不把本地通过当成远端 CI 通过。
