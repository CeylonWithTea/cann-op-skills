# 目录与记录

## 目录约定

```text
<工作区>/
├── ops-cv_<算子>/                     # 源码；可为同一 Git 仓库的 worktree
└── support_docs_<算子>/
    ├── README.md                     # 当前状态、长期约定、复现入口
    ├── issue.md                      # 需求与设计；使用仓库当前模板
    ├── pr.md                         # 最终改动、验证、限制与关联 issue
    ├── references/                   # 调研资料与数据格式表
    ├── reports/                      # 设计、迭代记录、自审结果
    ├── performance/                  # 逐例性能表、环境与测量摘要
    └── scripts/                      # 不属于正式交付的支撑工具
```

目录按需创建。其他仓采用 `<仓名>_<算子>`。已有仓名、分支、支持目录或 `ISSUE_DESCRIPTION.md` / `PR_DESCRIPTION.md` 原样继承，不为统一名称搬迁历史文件。

当前实现遵循目标仓的 op_host/op_kernel/op_api/tests/docs 等结构；先核对构建约定。自动生成 ACLNN 的仓库不能仅因没有手写 op_api 就被判定缺失接口，仍须验证生成头文件、符号、示例和打包可用。

多个算子共用同一个上游仓库时优先复用主 fork，各自独立分支/worktree。环境相同可共享工具链，每个算子独立构建输出、安装包路径和运行结果，避免同名包覆盖及旧包串用。不能通过修改共享构建脚本来掩盖本地环境问题。

## 最少记录

1. README：当前版本、任务约定、实际环境入口、已验证范围、下一步和复现命令。
2. 数据格式表：来源及语义差异一并说明。
3. `reports/迭代记录.md`：连续追加每个成功 demo 和重要失败尝试，自审结论可直接放在本版条目，不强制另建文件。
4. `performance/`：原始计时样本或足以复核统计的精简数据、逐例对比表、环境与源码标识。
5. issue/PR 正文：阶段性更新，提交前与最终源码及验证结果核对。

修复历史缺陷时记录“旧版本触发 → 修复 → 相同用例通过”；无法重跑旧版则明确证据限制。

## demo 封存与复现

优先保存 Git commit/tag 或可应用到已知基线的补丁。沿用项目已有 `experimental/demos/demoN` 时，仅复制必要源码和说明，避免复制 build、安装包及巨量输入输出。未跟踪或未提交源码必须有补丁/快照及内容 hash，单独一个 HEAD 不能代表工作区代码。

封存条目至少包括：

```text
demoN：目标与改动；支持范围变化；源码 commit/补丁标识；构建/包标识；
UT 与数值结果；自审问题和处理；基线/上一版比较及慢例；复现命令和结果路径。
```

每次尝试不必生成独立设计、执行、验收三套报告。历史结果注明对应源码、环境和用例集，不能贴到新的 HEAD 上当作新测试。旧 demo 若被新用例否决，追加失效原因，不删除原结论掩盖过程。

保留关键可执行用例、生成器、golden、benchmark 和失败反例。临时包、冗余日志和大图输出可在提取必要证据后按既有清理授权处理；不能删除唯一复现材料或其他任务产物。检查容器生成文件对宿主用户可读。

继承任务时先读 README、当前 diff 和最后一版记录，再按需查原始日志。不要每次加载整份历史聊天。新设备重测后追加新环境记录，保留历史数据的版本边界。
